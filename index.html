A scanner you already run, read as a hunting sensor

Three ways in. Start with the two charts below to see where the data is; use the platform tabs when you already know which plugin you need; use the ATT&CK matrix when you know which technique you are hunting and need to find the data for it. Search (/ or Ctrl+K) reaches all of it at once.

Why INFO plugins are the hunting layer

A vulnerability finding tells you a host could be attacked. An INFO plugin tells you what is actually on the host right now: which binaries auto-start, which processes are unsigned, which USB sticks have ever been plugged in, who is in the local Administrators group. Nessus already collects most of it during a normal scan — it just lands in the noise bucket that most teams filter out.

Used deliberately, that data gives you three things an EDR usually does not: coverage of hosts with no agent, a fleet-wide baseline you can diff week over week, and registry-resident artifacts (ShimCache, UserAssist, ShellBags, mounted device history) that survive the process exiting.

How to read a plugin row

Each row shows the plugin ID (linking to tenable.com), the exact plugin name, and what it returns. Open the row for the hunting use, the ATT&CK techniques it speaks to, a sample of the plugin output, and a pivot you can run in Tenable Vulnerability Management or Nessus.

core marks the highest-value plugins — the ones the playbooks are built from.

sensor agent + scanner says which sensors collect it. A plugin marked sensor scanner needs a scanner with network credentials and will never appear in agent results.

The grey monospace badge is the plugin family, which is what you enable in the scan policy.

Sample outputs are written to match each plugin's reporting format and are illustrative, not captured from a live host. Field layout shifts between plugin revisions — treat the shape as the contract, not the spacing.

Coverage map 0 hunting questions

Read this before you promise a hunt. Four verdicts, and the difference between the last two is what most coverage tables get wrong: Covered — a plugin returns the artifact. Partial — a plugin returns some of it, but not the part a hunter wants. Audit file — no plugin exists, but a compliance .audit check reaches it, so the data is available if you run a compliance scan. Nothing — not reachable from Nessus at all; this needs an EDR or a forensic pull.

Each verdict was tested against Tenable's plugin API rather than the site search: the complete Windows family (8,629 plugins) and the entire MacOS X Local Security Checks family (3,482) were enumerated and searched by name, synopsis and description, with cross-family checks across every sensor, and each surviving candidate verified at /plugins/api/v1/nessus/<id>. Plugins by platform›Windows

Windows

This is where Nessus enumeration is genuinely deep. Two plugin blocks carry most of the hunting value and both are easy to miss: 70613–70630 (the AutoRuns family, gated by 70627 AutoRuns Setup) and 92413–92439 (registry-resident execution and file-activity artifacts). Both need SMB credentials plus a reachable Remote Registry service.

Plugins by platform›Linux / Unix

Linux / Unix

Fewer plugins than Windows, but two of them are among the best single hunting signals Nessus produces: 33851 (listening daemons whose binaries are not owned by any package) and 110483 (a full ps auxww snapshot). Sudo matters here — without privilege escalation, 102094 will tell you exactly which commands were refused.

Plugins by platform›macOS

macOS

macOS coverage is better than its reputation, and worse in one specific place. Inventory, accounts, processes and listeners are all genuinely covered: 95929 returns every local and service account, and 110483 returns the full process list on a Mac despite being named for Unix/Linux. What is missing is persistence and security configuration — LaunchAgents, LaunchDaemons, kernel and system extensions, MDM profiles, TCC grants, SIP and firewall rules have no plugin between them.

Plan around this: macOS persistence hunting cannot be done from Nessus plugin output. Use a CIS/NIST .audit file for SIP, Gatekeeper and firewall state, and an EDR for ~/Library/LaunchAgents and kernel extensions. For everything else, 110483 gives you the process list, 121029 and 121032–121034 partition it by code-signing verdict, and 71264 flags processes never seen before in the estate.
Plugins by platform›Cross-platform

Cross-platform

Nobody hunts with these directly, and every hunt is worthless without them. They answer the question you get asked first: did the scan actually authenticate, on which hosts, and which plugins really ran? A host that quietly failed credentialed checks looks identical to a clean host in a findings export — 19506, 112154 and the Target Credential family are how you tell them apart.

Plugins with no technique, and why they still matter

A large part of this handbook maps to no ATT&CK technique at all, and leaving those out would be the wrong lesson. They fall into four roles, and a hunt fails without them:

  • Coverage proof and coverage gap — 19506, 112154, 141118, 110385, 24786, 102094, 26917, 135860. These decide whether a “no findings” result means clean or means not collected. Every technique cell above is worthless on a host where these say the scan did not work.
  • Prerequisite — 70627, 10400, 24269. Gates. When the gate is shut, a whole block of techniques silently drops out of your matrix.
  • Timeline and asset context — 92369 (time zone), 92366 and 56468 (boot time), 34096, 86420, 131568. Not detections; the difference between an artifact and evidence you can put in a timeline.
  • Extension point — 21156, 24760, 66756. Audit files are how you reach the artifacts the coverage map marks Audit file — cron jobs, systemd timers, kernel modules, audit policy, macOS SIP and the macOS firewall among them.
Detection view›Hunt playbooks

Seven hunts you can run from scan data alone

Each playbook is a plugin set plus the thing that makes a row suspicious. None of them needs a new tool — only that Info results are kept and that you export the plugin output column. The pattern that works in practice is a weekly export per plugin ID, diffed against last week: a new autorun on one host out of 4,000 is the finding, not the autorun itself.

PLAYBOOK 01

Fleet-wide persistence sweep

The AutoRuns family gives you Sysinternals-grade autostart coverage on every credentialed host, in one table.

Plugins
70627 70621 70625 70626 70618 70614 70629 70628 44401 204960
What makes a row suspicious
  • Autostart target under %APPDATA%, %TEMP%, C:\Users\Public, ProgramData or a path with no company name
  • Service ImagePath that is an unquoted path with spaces, or that wraps cmd.exe /c, rundll32, powershell -enc
  • A driver outside \SystemRoot\System32\drivers, or a signed-but-vulnerable driver name (BYOVD)
  • An IFEO Debugger value under 70618 — almost never legitimate outside developer machines
  • 70628 across the fleet: any unique entry with a count of 1 deserves a look
PLAYBOOK 02

Execution evidence without an image

Registry-resident execution artefacts outlive the process. This is how you answer “did this binary ever run here” on a host you cannot take offline.

Plugins
92415 77668 92435 92424 92423 92417
What makes a row suspicious
  • LOLBins with an unusual parent path: mshta, regsvr32, rundll32, certutil, bitsadmin, wmic, msiexec launched from a user directory
  • ShimCache or Prefetch entries for a file that no longer exists — deleted tooling
  • Archive utilities (7z, rar, winscp) on a host whose role never needs them
  • UserAssist run counts > 1 for something a user should never have opened twice
  • Prefetch names that differ from the on-disk binary name by one character
PLAYBOOK 03

Lateral movement reconstruction

Who reached what, from where. RDP client history plus mapped drives plus live sessions is a surprisingly complete movement graph.

Plugins
92433 92422 92373 92375 161502 58651 10395 60119
What makes a row suspicious
  • RDP history on a workstation pointing at domain controllers, jump hosts or hosts in another business unit
  • ADMIN$ / C$ / IPC$ mapped as a drive on an endpoint
  • A service account SID in 161502 — service accounts should not have interactive profiles loaded
  • Non-IT hosts with established connections to 445, 135, 5985, 3389 across many peers

PLAYBOOK 04

Staging and exfiltration

Collection and exfil leave file-dialog and archive-tool residue long after the files are gone.

Plugins

What makes a row suspicious
  • WinRAR/7-Zip history naming archives built from UNC paths or from a department share

PLAYBOOK 05

Unmanaged and unsigned code

The strongest single question in this whole atlas: what is running that no package manager or certificate accounts for?

Plugins
33851 104856 105045 70768 70943 121029 70331 196906
What makes a row suspicious
  • 33851 is nearly always worth reading line by line: a listening daemon outside the package database is either shadow IT or an implant
  • Unsigned or unverifiable processes (104856, 105045) running from outside Program Files
  • 70943 — a process never seen in prior scans of the fleet, on one host
  • 70331 modules: a DLL loaded from a user path into a Microsoft-signed process
  • macOS 121029 code-signing failures on binaries you did not build
PLAYBOOK 06

Credential exposure and privilege sprawl

Where the next hop comes from. This is the hunt that most often produces action before an incident rather than after.

What makes a row suspicious

PLAYBOOK 07

Defensive control drift

Attack paths open because a control quietly turned off on 40 hosts. These plugins find that before the hunt needs to.
