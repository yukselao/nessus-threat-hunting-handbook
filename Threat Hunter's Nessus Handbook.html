Why INFO plugins are the hunting layer

A vulnerability finding tells you a host could be attacked. An INFO plugin tells you what is actually on the host right now: which binaries auto-start, which processes are unsigned, which USB sticks have ever been plugged in, who is in the local Administrators group. Nessus already collects most of it during a normal scan — it just lands in the noise bucket that most teams filter out.

Used deliberately, that data gives you three things an EDR usually does not: coverage of hosts with no agent, a fleet-wide baseline you can diff week over week, and registry-resident artifacts (ShimCache, UserAssist, ShellBags, mounted device history) that survive the process exiting.

Plugins by platform›Windows

Windows

This is where Nessus enumeration is genuinely deep. Two plugin blocks carry most of the hunting value and both are easy to miss: 70613–70630 (the AutoRuns family, gated by 70627 AutoRuns Setup) and 92413–92439 (registry-resident execution and file-activity artifacts). Both need SMB credentials plus a reachable Remote Registry service.

Plugins by platform›Linux / Unix

Linux / Unix

Fewer plugins than Windows, but two of them are among the best single hunting signals Nessus produces: 33851 (listening daemons whose binaries are not owned by any package) and 110483 (a full ps auxww snapshot). Sudo matters here — without privilege escalation, 102094 will tell you exactly which commands were refused.

Plugins by platform›macOS

macOS

Set expectations before you scope a Mac hunt. The realistic ceiling from Nessus is software inventory, privileged-group membership, listeners, Chrome extensions and code-signing failures. There is no plugin for LaunchAgents, LaunchDaemons, kernel or system extensions, a full process list, MDM profiles or TCC grants — those are audit-file or EDR territory.

Plan around this: macOS persistence hunting cannot be done from Nessus plugin output. Use a CIS/NIST .audit file for SIP, Gatekeeper and profile state, and an EDR for ~/Library/LaunchAgents. Plugin 121029 (process code-signing failures) is the closest thing to a process-level signal.
Plugins by platform›Cross-platform

Cross-platform

Nobody hunts with these directly, and every hunt is worthless without them. They answer the question you get asked first: did the scan actually authenticate, on which hosts, and which plugins really ran? A host that quietly failed credentialed checks looks identical to a clean host in a findings export — 19506, 112154 and the Target Credential family are how you tell them apart.

Plugins with no technique, and why they still matter

A large part of this handbook maps to no ATT&CK technique at all, and leaving those out would be the wrong lesson. They fall into four roles, and a hunt fails without them:

  • Coverage proof and coverage gap — 19506, 112154, 141118, 110385, 24786, 102094, 26917, 135860. These decide whether a “no findings” result means clean or means not collected. Every technique cell above is worthless on a host where these say the scan did not work.
  • Prerequisite — 70627, 10400, 24269. Gates. When the gate is shut, a whole block of techniques silently drops out of your matrix.
  • Timeline and asset context — 92369 (time zone), 92366 and 56468 (boot time), 34096, 86420, 131568. Not detections; the difference between an artifact and evidence you can put in a timeline.
  • Extension point — 21156, 24760, 66756. Audit files are how you reach the techniques the coverage-and-gaps tab lists as unreachable.

Seven hunts you can run from scan data alone

Each playbook is a plugin set plus the thing that makes a row suspicious. None of them needs a new tool — only that Info results are kept and that you export the plugin output column. The pattern that works in practice is a weekly export per plugin ID, diffed against last week: a new autorun on one host out of 4,000 is the finding, not the autorun itself.

Getting the data out

The plugins above run in an ordinary credentialed scan. What usually stops teams is not the scan policy — it is that Info results get trimmed on the way to the dashboard, and that the plugin output column is left out of the export. The payload is the plugin output.

Scan policy checklist

  1. Give it credentials that can actually read

    Windows: an account with local admin on the target — 24786 fires when the scan ran without admin rights and the enumeration will be partial. Linux/macOS: SSH plus sudo or su; 102094 lists the exact commands that were refused.

  2. Make the Windows transports reachable

    SMB and the Remote Registry service for the registry-based plugins, DCOM/WMI for the WMI ones. 10400 and 26917 tell you about the registry, 24269 and 135860 about WMI. Nessus can start the Remote Registry service for the duration of the scan and stop it again afterwards.

  3. Do not run a template that trims plugin families

    The AutoRuns and forensic-artifact blocks live in the Windows family; the credential and patch-assessment plugins live in Settings; hostname, CPE and netstat parsing live in General. Use an Advanced Scan with all families enabled. The Malware Scan template is what you want for the reputation plugins (70767, 70768, 70943) and for your own hash list (65548).

  4. Leave thorough tests on

    Some plugins — 110231 among them — only run when thorough tests are enabled.

  5. Keep Info severity in the export

    This is where most of these programmes die. Saved searches, dashboards and export filters routinely exclude info. If Info is filtered, every plugin in this atlas disappears silently.

  6. Include the plugin output column

    Plugin ID and host alone tell you nothing here — the finding is inside the output text. In Nessus, export CSV with Plugin Output selected. In Tenable Vulnerability Management, add the Plugin Output column in Explore → Findings, or pull it from the API.

  7. Prove collection on every run

    19506 (scan settings and whether credentialed checks succeeded), 112154 (every plugin that actually launched on the host), 141118 / 110095 (credentials valid, no privilege issues), 117887 (patch assessment available), 152742 / 152743 (Unix discovery commands). A host that failed authentication looks exactly like a clean host unless you check these.

  8. Baseline, then diff

    One snapshot of 70621 across 4,000 hosts is a spreadsheet. The same export week over week, diffed, is a detection. Store per plugin ID + host + output hash and alert on new rows.

Pulling one plugin's output for the whole fleet

pyTenable against Tenable Vulnerability Management. Note the explicit severity filter — without it, an export configured elsewhere in your tenancy may drop Info findings.

python · pytenable
# Every AutoRuns Logon entry across the estate, ready to diff
from tenable.io import TenableIO
import csv, hashlib

tio = TenableIO()                      # TIO_ACCESS_KEY / TIO_SECRET_KEY
PLUGINS = [70621, 70625, 70626, 70618, 44401]

with open("autoruns_baseline.csv", "w", newline="") as fh:
    w = csv.writer(fh)
    w.writerow(["asset", "plugin_id", "first_found", "output_sha1", "output"])
    for f in tio.exports.vulns(severity=["info"], plugin_id=PLUGINS):
        out = (f.get("output") or "").strip()
        w.writerow([
            f["asset"].get("hostname") or f["asset"]["uuid"],
            f["plugin"]["id"],
            f["first_found"],
            hashlib.sha1(out.encode()).hexdigest()[:12],
            out.replace("\n", " | "),
        ])

Where to click instead

  • Tenable Vulnerability Management — Explore → Findings → Vulnerabilities, filter Severity = Info and Plugin ID = 70621, then add the Plugin Output column and export.
  • Nessus Professional — open the scan, Vulnerabilities tab, search the plugin name, then Export → CSV with Plugin Output ticked. Per host, the same data sits under the host's plugin list.
  • API, one plugin, one scan — GET /workbenches/vulnerabilities/{plugin_id}/outputs returns the output grouped by host, which is the fastest way to eyeball a single artefact class.
  • Agents — agent scan results carry almost all of this. The exceptions are the handful of scanner-only plugins (10150 and 237981 among them) that need a network vantage point or run only from a scanner.
A word on volume. Turning these on across a large estate produces a very large number of Info findings — the forensic block alone can add dozens per host, and 70624 returns a CSV report per host. Pick the plugin sets from the playbooks you will actually run, schedule them on their own scan policy, and export by plugin ID rather than dumping every Info finding into a SIEM.
